PERFORMANCE AND BUNDLE GATES

First measure the exact accepted OT-60 baseline before code changes. Then create numeric route-specific budgets and enforce them in tests/scripts. Use the strongest accepted evidence and the rules below; tighten rather than relax when the baseline is stronger.

Required test profile for primary mobile evidence:

- Chromium at `390x844`;
- realistic 150 ms network latency, 1600 kbps download, 750 kbps upload, and 4x CPU throttle, unless the accepted test harness defines a stricter equivalent;
- explicit warm-up followed by at least 30 measured samples for cold/first-usable and warm-return journeys;
- p50, p75, and p95, with raw sanitized samples retained;
- synthetic local data through real integrated APIs/repositories, not a static component timer mislabeled as application performance.

Minimum absolute gates unless accepted evidence is stricter:

- first useful owner/admin route and Dashboard p75 at or below 2.5 seconds;
- route transition with already-loaded shell p75 at or below 500 ms;
- warm return to a valid cached route p75 at or below 1.5 seconds, with a target of 500 ms when no network read is required;
- LCP at or below 2.5 seconds;
- CLS at or below 0.10;
- no initial long task over 200 ms;
- no horizontal page overflow;
- existing CRM list/detail p75 may not regress more than 10 percent from the strongest valid accepted baseline and may never exceed the absolute gate;
- public bundles remain free of authenticated app code.

Bundle budgets:

- Record gzip and, where supported, brotli sizes for shared shell, Dashboard route, and every module route chunk.
- Lock a numeric budget file into tests. The shared shell may not grow more than 10 percent over the accepted shell-critical baseline without a documented, measured necessity and compensating removal. Existing route chunks may not grow more than 10 percent without the same proof.
- Set a tight explicit budget for the new Dashboard route based on its implemented code, no-new-dependency design, and measured output; do not set the budget merely to the current size plus unlimited headroom.
- Fail builds on eager provider/portal/Telegram/worker imports or an unexpected module merged into the shared initial chunk.
- Inspect Vite/Rollup manifests, emitted HTML, preload tags, and source/import graphs, not only total `dist` size.

Request budgets:

- Critical Dashboard data: session/bootstrap plus one Dashboard-summary request, unless the accepted server can safely combine them into fewer. No per-module browser fanout.
- Shell-only transition: no unrelated module API requests.
- A selected module route requests only its own bounded bootstrap/data and shared session data required by the accepted architecture.
- CRM Overview does not request notes, tasks, relationships, identity, or communications until selected.
- Record exact request counts, paths with sensitive portions redacted, initiators, transfer sizes, cache modes, and waterfall timing.

The final evidence must prove cold entry, warm return, partial slow widget, partial failure, and navigation while a widget is pending.
